# DPE infrastructure

AWS resources of the Data Processing and Engineering team: the Managed Airflow (MWAA) environments, the S3 buckets the orca-recipes DAGs write to, and the S3 buckets that receive the Synapse RDS snapshots for Snowflake. The code is OpenTofu, run by Terragrunt, and Spacelift plans and applies it.

## Layout

```
apps/dpe/infra/
├── project.hcl                  # included by every unit: region, account IDs, DAG buckets, AWS provider
├── mwaa/{dev,prod}/             # one Terragrunt unit per Spacelift stack
├── dag-buckets/{dev,prod}/
├── snowflake/{dev,prod}/
├── modules/
│   ├── mwaa-stack/              # root module of the mwaa units
│   ├── dag-buckets-stack/       # root module of the dag-buckets units
│   ├── snowflake-stack/         # root module of the snowflake units
│   ├── mwaa/                    # modules the root modules source
│   ├── s3-bucket/
│   └── snowflake-s3-bucket/
└── spacelift-admin/             # the root admin stack: every Spacelift stack, space and AWS integration
```

## Stacks

| Spacelift stack            | Unit               | AWS account |
| -------------------------- | ------------------ | ----------- |
| DPE Managed Airflow dev    | `mwaa/dev`         | DNT dev     |
| DPE Managed Airflow prod   | `mwaa/prod`        | DPE prod    |
| DPE DAG Buckets dev        | `dag-buckets/dev`  | DNT dev     |
| DPE DAG Buckets prod       | `dag-buckets/prod` | DPE prod    |
| Synapse RDS Snapshots dev  | `snowflake/dev`    | DPE prod    |
| Synapse RDS Snapshots prod | `snowflake/prod`   | DPE prod    |

The Root Spacelift Administrative Stack runs `spacelift-admin/`. It creates and changes the stacks above. It does not run them.

## How a change is deployed

- A push triggers a stack when it changes a file that the stack's plan reads: a file in its unit directory, `project.hcl`, or the `*.tf` files of the modules it sources. These are the `additional_project_globs` in `spacelift-admin/deployments/<component>/main.tf`. When a root module starts sourcing another module, add that module to the list.
- Every stack has `autodeploy = false`, so nothing is applied until someone confirms the run. A run that plans no changes finishes on its own.
- A pull request gets a proposed run on each stack it triggers. The dev stacks of MWAA and DAG Buckets allow run promotion, so you can apply a branch to dev before merging. Their prod stacks only apply `main`.
- Spacelift manages the state of each stack, so there is no `remote_state` block. Deleting a stack deletes its state. Every stack sets `protect_from_deletion = true`. To remove one, set it to `false` and apply before you delete its module call.

## Where values live

- **Values of one environment**: the `inputs` of the unit, for example `mwaa/prod/terragrunt.hcl`.
- **Values that several units read**: the `locals` of `project.hcl`. These are the region, the AWS account IDs and the DAG buckets. The DAG buckets are listed once because the dag-buckets units create them and the mwaa units give the MWAA execution role access to them.
- **`orca_recipes_sha`**: `modules/mwaa-stack/main.tf`. Dev and prod share it, so they cannot diverge.
- **AWS provider**: generated by `project.hcl`. It sets `allowed_account_ids` to the unit's `aws_account_id`, so a plan fails when the stack's AWS integration is for another account.

## Check a change locally

The dev container has Terragrunt. In a unit directory:

```bash
terragrunt validate
```

A local `terragrunt plan` needs credentials for the unit's AWS account. It cannot read the stack's state, so it shows every resource as new. To see the real changes, read the stack's proposed run in Spacelift.

## Add a stack

1. Write the root module in `modules/<name>-stack/`. It must declare `region` and `aws_account_id`, because the generated provider reads them.
2. Add the units `<name>/dev/terragrunt.hcl` and `<name>/prod/terragrunt.hcl`. Copy an existing unit and change `source` and `inputs`.
3. Add `spacelift-admin/deployments/<name>/`. Copy an existing one and set its `additional_project_globs`.
4. Call it from `spacelift-admin/deployments/main.tf` with the AWS integration of each environment.
5. Merge the pull request and confirm the admin stack's run. Then confirm the first run of each new stack.

## Connect a new AWS account

Reference: <https://docs.spacelift.io/integrations/cloud-providers/aws#setup-guide>

1. Create a new IAM role (e.g., `spacelift-admin-role`) with description: "Role for Spacelift CI/CD to assume when deploying resources managed by Terraform"
2. Use this custom trust policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::324880187172:root"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringLike": {
          "sts:ExternalId": "sagebionetworks@*"
        }
      }
    },
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::{{AWS ACCOUNT ID}}:root"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

3. Attach these policies to the role:
   - `PowerUserAccess`
   - An inline policy for IAM operations (needed if Terraform creates/edits/deletes IAM roles/policies):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "iam:*Role",
        "iam:*RolePolicy",
        "iam:*RolePolicies",
        "iam:*Policy",
        "iam:*PolicyVersion",
        "iam:*OpenIDConnectProvider",
        "iam:*InstanceProfile",
        "iam:ListPolicyVersions",
        "iam:ListOpenIDConnectProviders",
        "iam:UpdateOpenIDConnectProviderThumbprint",
        "iam:ListGroupsForUser",
        "iam:ListAttachedUserPolicies"
      ],
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "iam:CreateUser",
        "iam:AttachUserPolicy",
        "iam:ListPolicies",
        "iam:TagUser",
        "iam:GetUser",
        "iam:DeleteUser",
        "iam:CreateAccessKey",
        "iam:ListAccessKeys",
        "iam:DeleteAccessKey"
      ],
      "Resource": "arn:aws:iam::{{AWS ACCOUNT ID}}:user/smtp_user"
    }
  ]
}
```

4. Add a `spacelift_aws_integration` resource to `spacelift-admin/common/aws-integrations/`.
